# صفحه مستقل ایمپورت تک‌محصول

لینک هدر تب `/imports/single?url=...` را باز می‌کند. POST و GET فقط به `/api/product/import/` می‌روند. پس از پذیرش، `job_id` در آدرس ذخیره می‌شود و refresh همان GET را ادامه می‌دهد. حتی دریافت slug یا پایان پردازش، صفحه را به `/products/...` منتقل نمی‌کند و API جزئیات محصول فراخوانی نمی‌شود. صفحه ایمپورت برای موتور جستجو noindex است.

لایه‌ها:
- service: اعتبارسنجی envelope، POST بدون retry خودکار، GET مطابق فاصله بک، کش مستقل هر job و نگه‌داشتن اطلاعات دریافت‌شده.
- useSingleProductImport: شروع/ادامه job، ذخیره شناسه در آدرس و تلاش مجدد. خطای موقت GET همان job را ادامه می‌دهد؛ تنها تلاش دستی پس از شکست قطعی می‌تواند POST جدید ایجاد کند.
- mapImportProductView: تبدیل داده ناقص به مدل نمایش مستقل؛ عنوان، گالری، قیمت یوان، تخفیف، قیمت پلکانی، مشخصات، وزن و اطلاعات فروشنده. مقدار ناموجود هرگز به قیمت صفر یا تبدیل ارز فرضی تبدیل نمی‌شود.
- view: نمایش تدریجی بخش‌ها با ProductDetailHero، ProductGallery، ProductSpecifications و ProductSupplierDetail مشترک. صفحه عادی محصول همچنان از useProduct و قرارداد خودش استفاده می‌کند.

قرارداد فعلی وضعیت جداگانه بخش‌ها ندارد. وجود داده معتبر یعنی قابل نمایش؛ نبود داده تا قبل از next_poll_after_seconds=0 یعنی انتظار، و بعد از صفر یعنی داده دریافت نشده. وضعیت done با فاصله مثبت هنوز polling دارد. هیچ درصد یا مرحله تکمیل ساختگی نشان داده نمی‌شود.

snapshotهای هم‌job ادغام می‌شوند: کلیدهای حذف‌شده حفظ می‌شوند، داده جدید جایگزین می‌شود؛ null و آرایه خالی موقت هنگام پردازش اطلاعات شناخته‌شده را پاک نمی‌کنند. در پاسخ نهایی null و آرایه خالی صریح اعمال می‌شوند. داده دو job هرگز ادغام نمی‌شود. این رفتار باید بعداً با قرارداد صریح snapshot/patch و وضعیت بخش‌ها هماهنگ شود.

جدول مشخصات فقط از `specifications` و مشخصات اصلی از `key_attributes` و `weight_kg` خوانده می‌شوند. کارت‌های فروشندگان دیگر، محصولات مشابه و دیدگاه‌های سایت مرجع به `other_sellers`، `related_products` و `comments` متصل‌اند. قیمت تومانی محصول اصلی و هزینه ارسال از سرویس‌های جداگانه دریافت می‌شوند. پاسخ ایمپورت موجودی، گزینه‌های قابل انتخاب، آمادگی خرید و قرارداد ثبت دیدگاه را ندارد.

## نیازهای بعدی قرارداد بک
وضعیت هر بخش (pending/ready/empty/failed)، معنای null و کلید حذف‌شده، شماره revision، اعلام آمادگی خرید همراه موجودی/گزینه‌ها و قیمت معتبر، و مقدار/نرخ تبدیل تومان در صورت نمایش قیمت ریالی. SSE برای نسخه فعلی لازم نیست.

# جستجو و ایمپورت کارت انتخاب‌شده

انتخاب یا drop عکس فقط فایل را اعتبارسنجی و آماده می‌کند. شروع درخواست و بازشدن تب، با کلیک مستقیم «جستجو با عکس» انجام می‌شود تا به transient activation رویداد change فایل یا drop وابسته نباشد. بازکردن تب در callback آپلود یا پس از انتظار برای API انجام نمی‌شود.

حالت عکس، نمای بزرگ‌شدهٔ خود ورودی جستجو است: نمای متنی هنگام بازبودن آن نامرئی می‌شود ولی فضای قبلی‌اش در هدر باقی می‌ماند. نمای عکس با عرض و مختصات همان ورودی شروع می‌شود و به پایین گسترش پیدا می‌کند؛ در موبایل برای خوانایی تا عرض مجاز صفحه باز می‌شود. جابه‌جایی و اسکرول با anchor مشترک هماهنگ است.

آیکون دوربین هدر `ImportImageSearch` را به‌صورت popover متصل به کادر جستجو باز می‌کند. پنل و لایهٔ کدر در portal هستند و ارتفاع هدر تغییر نمی‌کند. انتخاب فایل و drag & drop از یک مسیر مشترک استفاده می‌کنند؛ فقط یک عکس غیرخالی تا ۵ مگابایت پذیرفته می‌شود. فایل اصلی با `FormData.image` به `POST /api/products/import/image/` ارسال می‌شود؛ پیش‌فرض JSON کلاینت برای این درخواست حذف می‌شود تا مرورگر boundary را تنظیم کند. حالت بارگذاری، جلوگیری از ارسال هم‌زمان، خطا و انتخاب مجدد فایل پشتیبانی می‌شوند. بستن پنل یا خروج از صفحه درخواست در حال ارسال فرانت را لغو می‌کند (لغو job پذیرفته‌شدهٔ بک نیست).

جستجوی عکس و متن از `runImportSearch` برای باز کردن تب نتیجه استفاده می‌کند. پس از دریافت `job_id`، تب به `/imports/[jobId]` می‌رود. صفحه‌بندی عکس با cursor بک ادامه پیدا می‌کند و فایل در URL ذخیره نمی‌شود.

در `ImportHeaderInput` فقط جستجوی متنی با `query` به `POST /api/products/discover/` می‌رود. لینک مستقیم محصول از مسیر مستقل `/imports/single` که بالاتر توضیح داده شده استفاده می‌کند.

`useImportJob` فقط وضعیت جستجو را می‌گیرد و تا `done` یا `failed` مطابق `next_poll_after_seconds` ادامه می‌دهد. نتیجهٔ کامل‌شده در cache حفظ می‌شود. `useImportResults` با cursor صفحه‌های بعد را هنگام اسکرول درخواست می‌کند؛ صفحه‌های خالی با cursor معتبر ادامه داده می‌شوند. cursor تکراری متوقف می‌شود و خطای صفحهٔ بعد تلاش خودکار مکرر ندارد. اگر ورودی اولیه در لینک نباشد، ادامهٔ جستجو با خود cursor انجام می‌شود.

`mapImportJobPages` نتایج صفحه‌ها را بر اساس لینک منبع ادغام می‌کند، شناسهٔ نمایشی یکتا می‌سازد و job و candidate اصلی هر کارت را حفظ می‌کند. کارت ناقص هم نمایش داده می‌شود. صفحه از `ProductPage`، `ProductGrid` و `ProductCard` مشترک استفاده می‌کند؛ فیلتر و مرتب‌سازی روی کارت‌های دریافت‌شده است. مقادیر دریافت‌نشده قیمت، عکس، رنگ و فروشنده با مقدار فرضی جایگزین نمی‌شوند.

صفحهٔ نتایج هیچ اسکرپ جزئیاتی را در پس‌زمینه شروع نمی‌کند. محصول دارای slug مستقیماً به `/products/[slug]` می‌رود. انتخاب کاندید به `/imports/[ownerJobId]/product` با `candidate_id` و/یا `source_url` می‌رود و اسکلتون نمایش داده می‌شود. فقط آن صفحه `POST /api/products/jobs/{id}/candidates/import/` را برای کارت انتخاب‌شده ارسال می‌کند؛ endpoint عمومی `/api/product/import/` برای این مسیر استفاده نمی‌شود.

پاسخ شروع انتخاب در cache مستقل نگه داشته می‌شود تا تغییر route یا قطع GET موجب POST تکراری نشود. polling جزئیات با `GET /api/products/jobs/{id}/?compact=true` است. `done` بودن job جستجو، آماده‌شدن جزئیات کارت نیست. وضعیت همان candidate، `import_timeout` و `redirect_ready` بررسی می‌شوند؛ لینک محصول دیگری مصرف نمی‌شود. فقط مسیر داخلی محصول از slug یا URL جزئیات معتبر ساخته می‌شود. پاسخ آمادهٔ اولیه بدون GET اضافی redirect می‌شود.

خطای موقت polling برای تلاش دوباره همان job را حفظ می‌کند. شکست قطعی یا timeout خود کارت، cache شروع آن کارت را پاک می‌کند تا تلاش دستی دوباره به endpoint انتخابی برسد؛ بک نیز انتخاب تکراری در حال اجرا را deduplicate می‌کند. انتظار فرانت پس از پنج دقیقه با امکان تلاش دوباره متوقف می‌شود و این حالت job قبلی را نگه می‌دارد.

تست‌ها پاسخ API را شبیه‌سازی می‌کنند و job واقعی روی سرور ایجاد نمی‌کنند.
