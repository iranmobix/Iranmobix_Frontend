# جریان‌های Cart

## دریافت سبد

```text
/cart → CartPage → useCart → cartService.getCart
                                 ↓ انتخاب منبع
                    cartApi / cartMockApi
                                 ↓ unknown
                    cartResponseSchema.parse
                                 ↓ DTO معتبر
                            mapCart
                                 ↓ ServerCart
                      Query cache → Component
```

منبع اولیه همیشه `api` است. GET برای کاربر واردشده از اعتبار ورود و session مهمان موجود استفاده می‌کند؛ برای مهمان، ابتدا نشست معتبر موجود را استفاده می‌کند یا در نبود آن با POST /api/cart/session/ نشست می‌گیرد و هدر X-Guest-Cart-Token را به GET می‌فرستد. خطای نشست، GET را متوقف می‌کند و 401 باعث جایگزینی خودکار نشست موجود نمی‌شود. signal لغو درخواست از Query تا transport منتقل می‌شود. خطای HTTP یا schema به حالت خطا می‌رود؛ تلاش مجدد خودکار این query غیرفعال است، اما refetch معمول Query در mount/focus طبق تنظیمات provider ممکن است انجام شود.

پس از خطا، کاربر می‌تواند «تلاش دوباره» یا «نمایش دادهٔ نمونه» را انتخاب کند. هوک انتخاب منبع را نگه می‌دارد؛ کامپوننت mapper یا fixture وارد نمی‌کند. منبع نمونه از همان schema و mapper می‌گذرد و در `["cart", "mock"]` ذخیره می‌شود. بازگشت به API کلید `["cart", "current"]` را فعال می‌کند. انتخاب نمونه در reload حفظ نمی‌شود. اگر خود دادهٔ نمونه نامعتبر باشد، خطای قابل مشاهده و تلاش دوباره نمایش داده می‌شود؛ کاربر همچنان می‌تواند به API برگردد.

سبد خالی، loading، خطا و داده جدا رندر می‌شوند. خطای refetch ممکن است همراه دادهٔ قبلی دیده شود. در سبد واقعی، محصول و selected_options و pricing پس از validation مپ می‌شوند؛ نام/عکس/لینک و رنگ SKU در کارت نمایش داده می‌شود. دو رنگ یک محصول با id ردیف متفاوت مستقل می‌مانند. مبلغ هر ردیف از final_total_price با currency سبد گرفته می‌شود. جمع، تخفیف و تعداد از بک می‌آیند؛ checkoutReady فقط وضعیت را توضیح می‌دهد و چون قرارداد ثبت سفارش نداریم، ادامهٔ خرید فعال نمی‌شود.

## افزودن محصول

1. فرم مشترک محصول تعداد، شناسهٔ رشته‌ای رنگ/گارانتی و ویژگی‌های SKU را به AddToCartButton می‌دهد. ویژگی‌ها از product.price.attributes خوانده می‌شوند؛ نام و مقدار بدون ترجمه یا تغییر حروف در sku_attributes قرار می‌گیرند. فرم فقط گارانتی، تعداد و رنگ دارد؛ سایر ویژگی‌های SKU با اولین مقدار معتبر بک ارسال می‌شوند. گزینه‌های قدیمی یا ناشناخته با مقدار معتبر پیش‌فرض جایگزین می‌شوند؛ اگر برای ویژگی الزامی مقدار معتبری وجود نداشته باشد، دکمه غیرفعال است.
2. useAddToCart مالک guard محلی و وضعیت mutation مشترک است تا کلیک‌های تکراری UI محدود شوند.
3. useAddToCart خواندن در حال اجرای سبد واقعی را cancel می‌کند.
4. cartService.addItem ورودی را با addToCartSchema بررسی می‌کند؛ ورودی نامعتبر پیش از هر POST رد می‌شود.
5. ensureGuestCartSession یک نشست معتبر را استفاده می‌کند یا نشست جدید می‌گیرد.
6. cartApi.addItem درخواست را با slug کدگذاری‌شده و هدر مهمان می‌فرستد.
7. موفقیت POST کش سبد واقعی را invalidate می‌کند. خطای دریافت مجدد، موفقیت POST را به خطای افزودن تبدیل نمی‌کند.
8. در خطا دکمه پیام و لینک بررسی سبد نشان می‌دهد. POST خودکار تکرار نمی‌شود: timeout ممکن است پس از ثبت کالا رخ داده باشد.

guard رابط، idempotency سمت بک نیست. درخواست‌های مستقل add در سرویس حذف یا ادغام نمی‌شوند؛ تنها ساخت session هم‌زمان در یک تب مشترک می‌شود. محصول موک در فرم دیتیل نباید به سبد واقعی ارسال شود.

## چرخهٔ نشست مهمان

- storage key: `iranmobix.guest-cart.v1`.
- دادهٔ ذخیره‌شده: token، header و expiresAt بر حسب میلی‌ثانیه.
- mapGuestCartSession تبدیل خالص نشست را با زمان شروعِ دریافتی از سرویس انجام می‌دهد.
- پایان اعتبار: کمینهٔ expires_at بک و زمان شروع درخواست به‌علاوهٔ expires_in.
- خواندن در SSR مقدار null می‌دهد؛ ساخت/ذخیرهٔ نشست عملیاتی مرورگری است.
- JSON خراب، header نامعتبر یا نشست منقضی قابل استفاده نیست.
- اگر localStorage مسدود باشد، نشست تا زمان زنده بودن همین تب در حافظه باقی می‌ماند؛ reload آن را از بین می‌برد.
- حذف نشست توسط تب دیگر در خواندن بعدی رعایت می‌شود. listener برای پاک‌سازی خودکار Query سایر تب‌ها نداریم.
- Promise ساخت نشست در یک تب مشترک است و پس از موفقیت یا خطا آزاد می‌شود؛ هماهنگی ساخت نشست بین تب‌های مختلف وجود ندارد.

خطای ناشناختهٔ سرور باعث ساخت خودکار یک سبد تازه نمی‌شود. نگاشت خطای token نامعتبر/باطل‌شده به رفتار محصول هنوز قرارداد بک می‌خواهد.

## ورود و انتقال

`LoginForm → CartMergeAfterLogin → useCartMergeFlow → useMergeGuestCart → cartService.mergeGuestCart`

هوک flow شروع عملیات و navigation را نگه می‌دارد؛ کامپوننت فقط وضعیت و مسائل انتقال را نشان می‌دهد.

- پیش از merge، query جاری سبد cancel و از cache حذف می‌شود تا سبد قبلی به حساب جدید نسبت داده نشود.
- نبود session مهمان: سرویس بدون HTTP مقدار null می‌دهد؛ ورود به صفحهٔ اصلی ادامه می‌یابد.
- وجود session: POST merge با هدر مهمان و credentials مرورگر ارسال می‌شود. درخواست‌های هم‌زمان همین تب یک Promise مشترک دارند.
- نتیجهٔ معتبر ابتدا map می‌شود؛ cart برگشتی مستقیماً در cache واقعی قرار می‌گیرد.
- تعریف مسائل انتقال در getCartMergeIssues مشترک است: issues خود merge، سبد و همهٔ ردیف‌ها.
- فقط موفقیت بدون مسئله نشست را پاک می‌کند؛ clear به token درخواست وابسته است و نشست جدیدتر را حذف نمی‌کند.
- موفقیت کامل به `/cart` می‌رود؛ خطا/انتقال ناقص پیام و لینک بررسی سبد نشان می‌دهد و token حفظ می‌شود.

ورود، logout و refresh مسئولیت Auth هستند. این flow بعد از mount دوباره می‌تواند عملیات تازه‌ای شروع کند؛ guard آن تضمین سراسری یا دائمی برای یک‌بار اجرا نیست. حمل credentials به معنی تأیید موفقیت احراز هویت در بک نیست؛ [ابهام قرارداد](api-contract.md).

## پیش‌نمایش طراحی

`/cart/checkout → CheckoutPreviewPage → CartPreviewPage → useCartPreview / useCheckout`

CheckoutPreviewPage نقطهٔ ترکیب fixtureها و پیام واضح پیش‌نمایش است. reducer پیش‌نمایش تعداد، حذف، بازگردانی آخرین حذف، review و payment را محلی مدیریت می‌کند. route برای دیدن طرح پرداخت با مرحلهٔ اولیهٔ payment باز می‌شود؛ این مرحله نتیجهٔ تأیید واقعی کارشناس نیست.

فرم آدرس از React Hook Form و checkoutAddressSchema استفاده می‌کند؛ همان schema قبل از تغییر state هوک هم بررسی می‌شود. useCheckout مالک آدرس انتخاب‌شده، روش پرداخت، کد تخفیف و notice است. checkout.service محاسبات ریالی و امکان پرداخت را خالص محاسبه می‌کند. آدرس جدید فقط در state همین mount باقی می‌ماند. انتخاب روش پرداخت متن دکمه را تغییر می‌دهد؛ بدون callback واقعی فقط پیام پیش‌نمایش نشان داده می‌شود.

لغو سفارش، شارژ کیف پول، کوپن و پیش‌فاکتور این مسیر API ندارند. مودال کارت/شبا از Clipboard مرورگر استفاده می‌کند و خطای دسترسی را نشان می‌دهد. CheckoutDialog باز و بسته شدن dialog، Escape و بازگرداندن focus را مدیریت می‌کند.

## تغییر تعداد و حذف ردیف سبد

- `PATCH /api/cart/{item-id}` با بدنهٔ `{ "quantity": 99 }`؛ شناسهٔ ردیف سبد است، نه محصول یا catalog_id.
- `DELETE /api/cart/{item-id}` بدون بدنه.
- هر دو با credentials و توکن مهمان موجود ارسال می‌شوند؛ session تازه نمی‌سازند. مسیر بدون اسلش انتهایی مطابق قرارداد اعلام‌شده است.
- پاسخ mutation هنوز قرارداد مشخصی ندارد و unknown می‌ماند؛ mapper جدید ساختگی اضافه نشده است. پس از عملیات (حتی خطای مبهم شبکه) Query سبد واقعی invalidate و GET با schema/mapper فعلی اجرا می‌شود؛ Query موک دست‌نخورده می‌ماند.
- `useCartItemActions` درخواست هم‌زمان/تکراری را مسدود می‌کند، retry خودکار ندارد و تا پایان تازه‌سازی pending می‌ماند. خطا در صفحه نمایش داده می‌شود؛ GET ناموفق کنترل‌ها را تا دریافت موفق غیرفعال نگه می‌دارد.
- ورودی تعداد فقط با blur/Enter ثبت می‌شود، دکمه‌های +/- مستقیم درخواست می‌فرستند. عدد باید صحیح، مثبت و امن باشد؛ صفر جای حذف نیست. سقف موجودی فقط در صورت فعال بودن inventory_tracking_enabled اعمال می‌شود؛ بک مرجع نهایی اعتبار تعداد است.
- کنترل‌های سبد واقعی اکنون فعال‌اند؛ عبارت‌های تاریخی «API تغییر تعداد و حذف مشخص نیست» در بررسی‌های قبلی دیگر برقرار نیستند. دادهٔ نمونهٔ API همچنان قابل ویرایش شبکه‌ای نیست.

## مراحل سبد واقعی

CartSteps از دارایی assets/shape.svg استفاده می‌کند. بدون access token مرحلهٔ ورود، با وجود توکن مرحلهٔ ثبت اولیه و بعد از موفقیت submit مرحلهٔ انتظار بررسی کارشناس نمایش داده می‌شود. وجود توکن صرفاً وضعیت UI است و اعتبار آن را بک تعیین می‌کند. useAccessToken تغییرات storage و ورود/خروج در همان تب را دنبال می‌کند.

مرحلهٔ آخر «انتخاب آدرس و پرداخت» در نمایش مراحل آماده است؛ تا ارائهٔ قرارداد وضعیت سفارش و تأیید کارشناس، انتقال واقعی به پرداخت نداریم. وضعیت انتظار فعلاً به نتیجهٔ mutation همین صفحه وابسته است؛ بازیابی آن بعد از reload نیازمند API وضعیت سفارش است. مسیر preview همچنان صرفاً نمایش نمونه است.

تمدید خودکار با POST /api/auth/token/refresh/ به کلاینت مشترک متصل شد. درخواست دارای توکن پس از 401 حداکثر یک‌بار با access جدید تکرار می‌شود؛ بدنه، هدر مهمان و idempotency_key ثابت می‌مانند. شناسهٔ نشست ورود در تمدید ثابت است تا تلاش دستی بعدی نیز کلید سفارش را تغییر ندهد.


## ادامه بعد از ثبت اولیه

ثبت موفق → ذخیره tracking_code همراه رسید idempotency → دکمه «بررسی تأیید کارشناس و ادامه خرید» → /checkout/payment/{trackingCode} → GET اطلاعات پرداخت با حساب صاحب سفارش.

نبود ورود، لینک ورود با returnTo همان سفارش را نمایش می‌دهد. schema/دسترسی نامعتبر خطا می‌ماند و به موک تبدیل نمی‌شود. can_continue_payment و workflow و وضعیت approved مجوز مرحلهٔ پرداخت را تعیین می‌کنند؛ انقضا و خطای refetch نیز انتخاب روش را می‌بندند. روش‌های غیرفعال با دلیل بک نمایش داده می‌شوند. بررسی مجدد وضعیت دستی است؛ فاصله polling بک اعلام نشده است.

۷۴ تست آفلاین، شامل پاسخ واقعی نمونه، اختلاف قیمت، مجوز روش‌ها، محافظت هویت سفارش و حفظ کد پیگیری بعد از replay/reload، موفق‌اند. درخواست پرداخت واقعی در تست ارسال نمی‌شود.


مسیر اصلی سفارش اکنون /cart/{trackingCode} است. لینک ادامهٔ ثبت اولیه و returnTo ورود از همین مسیر استفاده می‌کنند. مسیر قدیمی /checkout/payment/{trackingCode} به مسیر جدید redirect می‌شود تا لینک‌های قبلی پیامک خراب نشوند. endpoint بک GET /api/customer/checkout/payment/{tracking_code}/ تغییری نکرده است. بک باید payment_page_url و لینک پیامک جدید را با مسیر /cart/{trackingCode} بسازد.


به‌روزرسانی انتظار کارشناس: پس از ثبت موفق دارای tracking_code، CartOrderSubmitted خودکار به /cart/{trackingCode} منتقل می‌شود؛ عنوان انتظار دیگر یک وضعیت ثابت محلی نیست. GET موفق با expert_pricing_status=pending_review در تب فعال هر ۱۵ ثانیه تکرار می‌شود. approved یا هر وضعیت دیگر و نیز خطای احراز هویت/شبکه/schema polling را متوقف می‌کند؛ دکمه بررسی مجدد باقی می‌ماند. قیمت منقضی حتی پس از تأیید قابل پرداخت نیست. ثبت‌های قدیمی بدون کد پیگیری به‌عنوان منتظر کارشناس معرفی نمی‌شوند.


### انتخاب روش پرداخت در طرح جدید
چهار روش آنلاین، کیف پول، کارت به کارت و حواله ارزی در فرانت تعریف می‌شوند؛ انتخاب نمایشی به payment_options وابسته نیست. موجودی کیف پول از پاسخ بک خوانده می‌شود. متن دکمه به ترتیب «پرداخت»، «پرداخت»، «بارگذاری رسید پرداخت» و «پرداخت حواله ارزی» است. اطلاعات کارت طبق درخواست کارفرما ثابت و در CHECKOUT_BANK_ACCOUNT مشترک است. عملیات پرداخت هنوز به endpoint متصل نشده؛ انتخاب روش به معنی پرداخت یا تأیید سفارش نیست. بخش پذیرش قرارداد تا دریافت متن یا لینک قرارداد غیرفعال است.


### روش‌های پرداخت از پاسخ بک
رفتار قبلی چهار گزینه ثابت در صفحه واقعی جایگزین شد: فقط options مپ‌شده از payment_methods نمایش داده می‌شوند؛ title، ترتیب، enabled و reason از بک هستند. گزینه غیرفعال نمایش داده می‌شود اما قابل انتخاب نیست؛ کد ناشناخته نیز غیرقابل انتخاب است. پاسخ خالی گزینه فرضی ایجاد نمی‌کند. انتخاب حذف‌شده یا غیرفعال، یا پنجره پرداخت نامعتبر، انتخاب معتبر برای ادامه نیست. چهار گزینه ثابت فقط در پیش‌نمایش بدون serverOptions باقی می‌مانند.
