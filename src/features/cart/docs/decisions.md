# تصمیم‌های معماری و راهنمای توسعه

## ۱. الگوی Auth، با رعایت مسئولیت‌ها

اصل مشترک، جداسازی API، service، mapper، type، schema، hook و component است. کلاس بودن AuthApi یا نام فایل‌های آن الزام cart نیست. پوشه و abstraction فقط برای نیاز واقعی ساخته می‌شود. به همین دلیل store خالی و cart-link خالی حذف شدند؛ اطلاعات سرور در Query و state محلی پیش‌نمایش در reducer می‌ماند.

معماری همهٔ فایل‌های فعلی در [architecture.md](architecture.md) آمده است. محدودیت‌های Auth را از روی راهنمای مشترک به‌عنوان قابلیت آماده فرض نکنید.

## ۲. جداسازی سبد واقعی و طراحی

مدل واقعی در cart.types.ts و مدل محاسباتی پیش‌نمایش در cart-preview.types.ts است. نام‌های ServerCart و ServerCartItem عمداً مفهوم واقعی را صریح می‌کنند. checkout.types.ts هنوز قرارداد محلی پیش‌نمایش است.

CartItem و CartList و CartSummary برای نمایش مشترک استفاده می‌شوند؛ UI ردیف‌ها دوباره‌نویسی نشده است. تفاوت دادهٔ واقعی/نمونه در ورودی مشخص است و رفتار ویرایش به callbackهای موجود وابسته است.

دو نوع نمونه داریم:

- **موک قرارداد API** برای /cart: adapter → schema → mapper → query با cache جدا.
- **پیش‌نمایش طراحی** برای checkout: fixture از جنس domain → reducer/checkout rules. این مسیر از API واقعی ادعا نمی‌کند و بنر آشکار دارد.

یک flag سراسری که همهٔ عملیات واقعی و پرداخت را مخلوط کند نداریم.

## ۳. منبع مبلغ و فیلد نامشخص

مبالغ سبد واقعی رشته‌های ده‌دهی دقیق بک هستند. Number، نرخ ارز حدسی و محاسبهٔ دوبارهٔ جمع استفاده نمی‌شود. جمع‌های نمونه از snapshot محلی برای نمایش طراحی محاسبه می‌شوند؛ formatCheckoutMoney فقط آن مدل ریالی را به تومان نمایش می‌دهد.

فیلدهای nested نامشخص unknown باقی می‌مانند. راه تکمیل آن‌ها دریافت JSON واقعی، type/schema و mapping دقیق است؛ استفاده از any یا مقدار نمونه در component راه‌حل نیست.

## ۴. session و mutation

ذخیره‌سازی نشست wrapper مستقل دارد تا کد UI به localStorage وابسته نشود. session فقط وقتی افزودن به آن نیاز دارد ساخته می‌شود. Promise مشترک، ساخت session و merge هم‌زمان را در همان تب هماهنگ می‌کند.

POST افزودن/انتقال retry خودکار ندارد. session معتبر موجود بعد از خطای مبهم کنار گذاشته نمی‌شود. تضمین exactly-once برای سفارش یا افزودن به سبد فقط با قرارداد idempotency بک قابل پیاده‌سازی است.

تعریف مسائل merge در getCartMergeIssues مشترک است؛ UI و منطق حذف token معیار متفاوت ندارند. token جدیدتر در پایان درخواست قدیمی پاک نمی‌شود.

## ۵. مالکیت cache و Auth

کلید واقعی `["cart", "current"]` و نمونه `["cart", "mock"]` مستقل‌اند. موفقیت add فقط کلید واقعی را invalidate می‌کند. شروع merge، cache واقعی قبلی را پاک می‌کند و cart پاسخ merge منبع جدید آن است.

**محدودیت فعلی:** کلید واقعی هنوز شناسهٔ مالک ندارد، با وجود مشخص شدن owner.type/user_id در پاسخ سبد، Auth وضعیت پایدار قابل استفاده پیش از query ندارد. پاک‌سازی روی ورود موجود است؛ logout، جابه‌جایی حساب و هماهنگی cache میان تب‌ها کامل نشده‌اند. هنگام اتصال Auth جدید باید identity در key یا سیاست پاک‌سازی همهٔ تغییرات حساب اضافه شود. بدون این کار cache حساب قبلی را برای حساب جدید معتبر فرض نکنید.

## ۶. public API و reuse

مصرف‌کنندگان cart از index.ts استفاده می‌کنند؛ exportهای بدون مصرف خارجی حذف شده‌اند. برای مصرف جدید، فقط قرارداد واقعاً مورد نیاز را export کنید. فایل‌های server-only آینده را در همان ورودی کلاینت قرار ندهید.

کامپوننت‌ها و مدل Product از فیچر محصول reuse می‌شوند. deep importهای فعلی محصول به خاطر نبود export عمومی مناسب باقی‌اند و در معماری ثبت شده‌اند؛ برای همسان‌سازی نام پوشه‌ها، Product را در cart کپی نکنید.

## راهنمای انتخاب فایل برای تغییر

| نیاز                   | ترتیب تغییر                                                                     |
| ---------------------- | ------------------------------------------------------------------------------- |
| کلید جدید پاسخ بک      | API type → schema → mapper → domain → fixture/test → UI → api-contract          |
| endpoint یا header     | cart.api.ts، تست transport و api-contract                                       |
| محدودیت تعداد یا شناسه | schema؛ برای UI قاعدهٔ مرتبط و نمایش خطا؛ تست ورودی نامعتبر                     |
| رفتار cache            | constants و use-cart-actions/use-cart؛ تست isolation و جریان Auth               |
| مراحل بعد از ورود      | use-cart-merge-flow و component وضعیت؛ منطق OTP در Auth بماند                   |
| متن یا layout سبد      | component مرتبط؛ domain برای کلاس CSS عوض نشود                                  |
| روش ذخیرهٔ session     | storage wrapper و session service، تست SSR/خرابی/انقضا                          |
| مقدار نمونهٔ API       | cart-api.mock.ts؛ schema را برای عبور دادن fixture ناسازگار ضعیف نکنید          |
| طراحی پرداخت           | checkout components، useCheckout و قواعد محلی؛ API جدید را از نوع موک حدس نزنید |

### نمونهٔ توسعه: تکمیل قرارداد تغییر تعداد واقعی

PATCH/DELETE متصل شده‌اند و پس از عملیات GET دریافت می‌شود. برای تکمیل پاسخ mutation و قوانین موجودی:

1. method/path، شناسهٔ ردیف، payload، پاسخ، خطای موجودی و سیاست idempotency را ثبت کنید.
2. در types/api قرارداد ورودی/خروجی و در schema اعتبار تعداد/پاسخ را اضافه کنید.
3. API فقط درخواست را بفرستد؛ service پاسخ را validate/map کند.
4. mutation در use-cart-actions وضعیت pending/error و تازه‌سازی cache را مدیریت کند. اگر پاسخ cart معتبر دارد همان را استفاده کنید؛ در غیر این صورت refetch طبق قرارداد.
5. CartQuantity/CartItem موجود را reuse کنید. حدود واقعی min/max باید از domain بک بیاید؛ مقدار حدسی از fixture نگیرید.
6. تا تعیین قانون rollback و concurrency، optimistic update اضافه نکنید.
7. تست ورودی مرزی، خطا، درخواست هم‌زمان، حفظ قیمت معتبر و اثر روی cache بنویسید.
8. قرارداد، flow و inventory docs را به‌روز کنید.

## کارهای باقی‌مانده

اولویت‌های اتصال واقعی: نمونه‌های غیر null باقی‌ماندهٔ قرارداد، قرارداد حمل احراز هویت با Auth جدید، cache حساب‌ها، سپس قرارداد پاسخ تغییر/حذف ردیف و ثبت سفارش. آدرس و پرداخت وقتی متصل شوند که DTO و قوانین معتبر بک آماده باشد. این ریفکتور این قابلیت‌ها را تکمیل‌شده اعلام نمی‌کند.
